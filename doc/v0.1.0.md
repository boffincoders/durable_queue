# Version 0.1.0

Status of the first release: what shipped, and what is still ahead.

`0.1.0` is the core engine. It proves a small, testable, framework-free task queue. It does not try to be a database, an HTTP client, or an OS background runner.

The design this version follows is [design.md](design.md). Runtime rules are in [execution-semantics.md](execution-semantics.md). Adapter rules are in [storage.md](storage.md).

## What shipped

Pure Dart. No runtime dependencies. SDK bound `^3.13.0`. MIT license. Package description is the public tagline from the design.

### Engine

- `DurableQueue` with `start`, `pause`, `resume`, and `stop`.
- Explicit states: `pending`, `running`, `retryScheduled`, `completed`, `failed`, `cancelled`.
- Unique task IDs (UUID v4, overridable).
- Task registry with JSON encode and decode. An unknown type at `enqueue` fails immediately. An unknown type already in storage fails permanently when the worker reaches it, so one bad record cannot block the queue.
- Handlers are `(task, context)`. `TaskContext` carries the attempt, the attempt budget, the idempotency key, the deduplication key, and a cooperative cancellation flag.
- Worker error isolation. One handler failure does not stop later tasks.
- Mutations are serialized. One active `DurableQueue` per storage.

### Persistence

- `QueueStorage` and `StoredTask`, including JSON that an adapter can store.
- `MemoryQueueStorage` for tests and process-lifetime queues.
- Storage contract tests that a future adapter can reuse.
- Startup recovery for tasks left `running`. A requested cancel becomes `cancelled`. Otherwise the interrupted attempt counts, and the task is either failed or scheduled with backoff. A crash loop cannot retry forever.
- Enqueue order is a persisted `sequence`. Eligible tasks run oldest `createdAt` first, then `sequence`, then id. Tasks stored in the same clock tick stay in insertion order.

### Reliability

- `RetryPolicy.none` (the default; one attempt), `fixed`, and `exponential`.
- Exponential backoff doubles from `initialDelay` and caps at `maxDelay`. Delays are capped at 365 days so scheduling cannot overflow.
- Jitter on exponential policies only. Fixed delays stay exact.
- `maxAttempts` includes the first run. `retryIf` can refuse another attempt. If `retryIf` itself throws, the task is not retried and the stored error stays the handler error.
- `maxConcurrentTasks`. A retry wait does not occupy a slot and does not block other pending work.
- Deduplication of active tasks (`pending`, `running`, `retryScheduled`). A duplicate enqueue returns the existing id and does not merge the payload. Terminal tasks do not block a later enqueue. Empty keys are rejected.
- `idempotencyKey` is stored and exposed on `TaskContext`. The core does not send it anywhere.
- Cancellation of a queued task is immediate and does not call the handler. Cancellation of a running task sets a flag and does not abort the Dart future. If that handler then returns, the task is `completed`. If it throws, including `TaskCancelledException`, the task is `cancelled` and is not retried.
- Queries by status. A broadcast event stream (`TaskEnqueued`, `TaskStarted`, `TaskRetryScheduled`, `TaskCompleted`, `TaskFailed`, `TaskCancelled`) emitted after the write. `TaskFailure` keeps the error, stack, time, and attempt.
- `QueueClock`, `SystemQueueClock`, and `FakeQueueClock`. Tests advance time instead of sleeping. There is no busy poll.

### Tests, example, and docs

- Deterministic tests for storage, serialization, retries, the scheduler, concurrency, deduplication, cancellation, recovery, the clock, and the definition of done. `dart analyze` is clean and the suite passes.
- Runnable `example/main.dart`: one task fails once, retries, and completes.
- Public README (quick start), CHANGELOG, CONTRIBUTING, execution semantics, and the storage contract.

Task timeout was optional in the 0.1.0 checklist and was left out. A handler that needs a deadline owns that deadline.

## Semantics to keep honest

- Delivery is at-least-once. A crash after a side effect and before the completion write can run the handler again.
- `MemoryQueueStorage` lives for the process. Tasks survive a new `DurableQueue` on the same storage object. They do not survive process death until a durable adapter exists.
- Persisting a task is not the same as the OS running the app after it is terminated.
- Sensitive payloads are the app's responsibility.
- Completed and failed tasks stay in storage. `0.1.0` has no queue-level delete.

## What is pending

These are later versions in the design. They are not part of `0.1.0`.

### v0.2.0 — production persistence

A separate package, likely `durable_queue_drift`: SQLite, migrations, indexed queries, transactional updates, and recovery that survives process death. Drift stays out of the core so apps can pick their own adapter. The storage contract in this repo is the checklist for that adapter.

### v0.3.0 — orchestration

Task dependencies, dependency-failure behavior, priorities, groups, and chains.

### v0.4.0 — Dio

A separate `durable_queue_dio` package: timeouts, connection failures, HTTP 429, `Retry-After`, 5xx, and Dio cancellation. Dio stays out of the core.

### v0.5.0 — Flutter

A separate `durable_queue_flutter` package: app lifecycle, resuming the queue when the app returns, Flutter bindings, and optional connectivity hooks.

### v0.6.0 — inspector

A developer-only `durable_queue_inspector`: counts by status, per-task attempt and retry time, and controls such as retry, cancel, delete, inspect payload, pause, and resume.

### Also deferred

HTTP interception, connectivity detection, Riverpod, Bloc, Hive, Isar, Android WorkManager, iOS BGTaskScheduler, background isolates, optimistic UI, mutation compaction, conflict resolution, a remote sync engine, distributed queues, and exactly-once delivery.

### Small follow-ups inside this package

- Document the `MemoryQueueStorage` constructor.
- Fix the four unresolved dartdoc links.
- Decide whether completed tasks need a retention or delete API. `0.1.0` keeps them.
- Publish only after the archive and repository checks above are clean.
